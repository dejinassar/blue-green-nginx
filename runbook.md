#  Operator Runbook: Blue/Green Observability Alerts

This document outlines the meaning of alerts generated by the `alert_watcher` service and the immediate actions an operator should take.

---

## 1. Alert Types and Meaning

| Alert Title | Trigger Condition | Meaning |
| :--- | :--- | :--- |
| ** FAILOVER DETECTED** | Nginx logs show an instantaneous switch in the primary pool serving traffic (e.g., `app_blue` → `app_green`). | **Unplanned Failover:** This usually means the previously active pool (Blue in this example) failed its health checks (e.g., 5xx errors, timeouts) and Nginx automatically routed traffic to the inactive pool (Green). **Immediate action is required.** |
| ** HIGH ERROR RATE** | The rate of 5xx upstream errors exceeds the configured threshold (e.g., >2%) over the sliding window (e.g., last 200 requests). | **Service Degradation:** The currently active pool is serving too many errors, but has not yet completely failed or triggered a failover. **Immediate attention is required.** |
| ** RECOVERY ALERT** | (Note: This is often implemented as the absence of the "HIGH ERROR RATE" alert after a cooldown period, or via a separate 'recovery' trigger). | The system has stabilized, and error rates have returned to normal or traffic has successfully switched back to the stable primary pool. |

---

## 2. Operator Actions by Alert

###  FAILOVER DETECTED (e.g., Blue → Green)

**Goal:** Determine if the failed pool is recoverable and stabilize the environment.

| Step | Action | Notes |
| :--- | :--- | :--- |
| **1. Investigate** | **Immediately check the health and logs of the FAILED container (`app_blue` in this example).** | Look for fatal errors, memory issues, or high resource consumption that caused the failure. |
| **2. Verify Switch** | Check the logs for the `app_green` container to ensure it is healthy and correctly serving 200 responses. | Confirm that Green is stable and traffic is flowing correctly. |
| **3. Decide** | **If FAILED pool (`app_blue`) is unrecoverable:** Terminate and rebuild `app_blue` with a known good image, or prepare for a rollback if the failure was deployment-related. | **If FAILED pool (`app_blue`) is recoverable:** Attempt a restart or self-healing action. |
| **4. Post-Mortem** | Log the event, timestamp, and root cause analysis for later review. |

###  HIGH ERROR RATE

**Goal:** Identify the cause of the errors and potentially initiate a manual switch before a full failure.

| Step | Action | Notes |
| :--- | :--- | :--- |
| **1. Investigate** | **Check the logs of the ACTIVE container (`app_blue` or `app_green`) for application-level errors (e.g., database connection failures).** | The error is originating from the application, not the load balancer. |
| **2. Check Inactive** | Check the logs of the INACTIVE container (`app_green` or `app_blue`) to ensure it is ready to take traffic. | A manual switch is the likely next step if the active pool cannot be saved. |
| **3. Triage** | If the error rate persists and is trending up, **manually switch traffic** to the stable, inactive pool by updating the `.env` file and running `docker compose restart nginx`. | **Preventative Failover.** This is better than waiting for an auto-failover. |

---

## 3. Maintenance Mode (Suppressing Alerts)

To prevent spam during planned activities (like a Blue/Green toggle), alerts can be temporarily suppressed.

**Action:**
1.  Before the planned switch/maintenance, set the `ALERT_COOLDOWN_SEC` in the `.env` file to a very large number (e.g., `999999`) or add a `MAINTENANCE_MODE=true` environment variable and check for it in `watcher.py`.
2.  Perform your planned deployment or switch.
3.  Once maintenance is complete, **immediately revert** `ALERT_COOLDOWN_SEC` to its default value (`300`).
